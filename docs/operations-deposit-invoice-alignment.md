# Operations → AP Deposit Invoice alignment

## Evidence boundary

This is **default-off AP readiness**, not a live cutover. The authoritative historical rules for this implementation are the user-supplied Operations history and the existing AP `financialWorkflowEngine.ts` Deposit evaluator (lines 430–447), `financialAutomationRules.ts` Deposit item (`Deposit Required`), and exact-number Xero preflight. The repository does **not** contain independently confirmed custom Deposit field API names or the complete legacy date-default implementation. No live VTiger/Xero lookup was performed during development; tests use mocked metadata/current records.

## Conservative mapping decisions that remain unresolved

1. The required custom API field names—**Deposit Status** and **Deposit Amount Required**—are deliberately resolved from current authenticated `describe(Potentials)` labels at runtime. Local fixtures such as `cf_real_status` are test-only, not real mappings. Required labels absent/duplicated or records omitting a mapped required field are held. The two date labels are optional and no alias is added for them.
2. The historical date sequence is known but two-date conflict precedence is not. Conflicting populated dates explicitly hold, preserving factual raw source dates. When both date fields are absent/unmapped, the Draft Due Date is deliberately empty; Issue Date currently uses AP UTC current date, matching the current Main invoice family pattern.
3. Current Deal organisation/contact mappings follow existing AP Main invoice mappings, without its Quote precedence. Record shape and exact ID are verified. No external schema verification was attempted in this task.
4. Deposit accounting configuration must be supplied by the current Xero sales item; the historical account number is not asserted. Review the GET-only evidence before approval.

## Isolation and immutable evidence

`financial_deposit_invoice_events` is additive and independent of Asset/Main ledgers. The source snapshot, mapping evidence, rules hash, GET-only preflight, proposal and deduction hold are append-only. Duplicate evidence insertion does only an evidence-key no-op. Exclusive nullable unique Deal/number claim keys prevent a second AP write across multiple preview receipts. The authorised payload is bound once with a hash and full body, and never replaced. Claim keys survive failures; there is no blind retry. The separately additive `financial_deposit_main_deduction_events` table does the same for the optional main-Draft update and has unique Deposit/main Xero resource evidence; it never changes a Deposit creation receipt.

Both pre-execution and pre-transport verification independently refresh the exact Deal/customer/metadata and Xero GET collision/contact/item/account evidence, compare immutable hashes, rebuild the exact payload, and re-check the standing release. Any source change, collision, release change or payload mismatch fails shut. Exact Draft read-back checks ACCREC, ID/number/status, contact, dates, Inclusive amounts, GST total, AUD, account and Deposit item.

The existing canonical `/api/financial-workflows/events/deposit-invoice` remains proposal infrastructure and does not receive the dedicated automatic authorisation. The guarded writer rejects Deposit commands and exact `-D` documents supplied by generic/other-family contexts.
